## D-001　管理后台「一键补齐模拟患者信息」功能损坏

| 项 | 内容 |
|----|------|
| 严重度 | **高**（用户可见功能完全不可用） |
| 位置 | `frontend/src/views/admin/sections/IdridImportSection.vue:142` |
| 发现方式 | 前端类型检查（`vue-tsc -p tsconfig.app.json`） |

**现象**

管理后台「IDRiD 批量导入」页中的「旧病例 · 一键补齐模拟患者信息」按钮，点击后必定报错，功能从未可用。

**根因**

前端调用了不存在的 API 函数，且后端也没有对应接口：

```
IdridImportSection.vue:142   await CaseImageApi.backfillPatientInfo({...})
                             ↑ frontend/src/api/case-image.ts 中未定义此函数
backend/app/api/v1/admin_import.py   仅有 POST /idrid，无补齐患者信息的路由
```

类型检查报错：

```
error TS2339: Property 'backfillPatientInfo' does not exist on type
              'typeof import(".../api/case-image")'
error TS2694: Namespace '".../api/case-image"' has no exported member
              'BackfillPatientResult'
```

**处理建议**

二选一，取决于该功能是否仍需要：

1. **补齐实现**：后端加 `POST /admin-import/backfill-patient`，支持 `onlyEmpty` / `overwrite` 两种模式（前端 UI 已按此设计），前端补 API 函数与类型；
2. **移除 UI**：若该功能已废弃，直接删掉相关按钮与调用，避免用户点到报错。

注：仓库中已有 `backend/scripts/backfill_case_sn_and_images.py`，可作为实现参考。

## D-002　无金标准标注的病例无法拿到满分

| 项 | 内容 |
|----|------|
| 严重度 | **中**（影响成绩公平性，但不影响功能可用） |
| 位置 | `backend/app/services/practice_service.py::_score` |
| 发现方式 | 补充 DR 分级测试时发现 |

**现象**

学员完全答对，总分也只有 85 分；对于没有病灶的病例（正常眼底、非 DR 病种），标注题永远拿不到满分。

**根因**

标注分公式为：

```python
score_annotation = accuracy * 70.0 + iou_avg * 30.0
```

当病例没有任何金标准标注时：

- `accuracy = 1.0`（学员没有漏标，判定为全对）
- `iou_avg = 0.0`（没有框可以计算 IoU）

→ 标注分恒为 `70.0`，连带总分上限变成 `100*0.3 + 70*0.5 + 100*0.2 = 85`。

**已固化**

该行为已由测试 `tests/test_dr_grade.py::test_known_issue_no_gold_annotation_caps_annotation_score_at_70` 显式固化，避免被误认为正常。修复时需同步更新该测试。

**处理建议**

修复方向：当 `iou_cnt == 0` 且不存在漏标时，IoU 分量应视为满分或从公式中剔除并重新分配权重（与本次「DR 分级不适用」的处理思路一致）。

**注意**：此改动会改变评分口径，影响历史成绩的可比性。建议与教学负责人确认后再执行，并明确是否重算历史记录。

## D-003　前端类型检查存在 47 处未使用变量

| 项 | 内容 |
|----|------|
| 严重度 | 低（无功能影响） |
| 位置 | 多文件 |

**现象**

`vue-tsc -p tsconfig.app.json --noEmit` 报告 47 处 `TS6133: declared but its value is never read`，另有 1 处 `TS2345`（`screening/case-search.vue:706`，`string | undefined` 传入要求 `string` 的参数，存在潜在运行时异常）。

**影响**

数量过多会掩盖真实错误——本次修复中就发生过：一处调用了不存在的函数 `loadSource()`（实际应为 `fetchSource()`），因淹没在噪声中且当时类型检查命令有误而未被及时发现。

**处理建议**

1. 清理未使用变量（多为未删除的图标引入与废弃的方法）；
2. 修复 `TS2345`；
3. 把 `vue-tsc -p tsconfig.app.json --noEmit` 纳入 CI，保持零错误。

## D-004　开发库从未被 alembic 纳管，迁移链未在任何环境验证过

| | |
|----|------|
| 严重度 | **高（部署时才会暴露）** |
| 位置 | `backend/edu_eye.db`、`backend/alembic/versions/` |

**现象**

开发库里没有 `alembic_version` 表——它是 `Base.metadata.create_all()` 建出来的，
而不是由迁移建的。0001～0008 这条迁移链从来没有被完整执行过，
每次加字段都是手工 `ALTER TABLE` 打上去的。

**影响**

生产首次部署执行 `alembic upgrade head` 时，整条链会第一次真正运行。
其中任何一处与当前模型不一致（字段类型、约束、索引名、SQLite 不支持的
`ALTER`），都会在部署现场才发现，且此时已经有数据。

**处理建议**

1. 在干净库上跑一遍 `alembic upgrade head`，与 `create_all()` 的结果做 schema diff；
2. 差异补成新的迁移，而不是改历史迁移；
3. 开发库 `alembic stamp head` 纳管，此后一律走迁移，不再手工 ALTER。

## D-005　alembic.ini 含中文，Windows 下无法读取

| | |
|----|------|
| 严重度 | 低（仅影响 Windows 开发机） |
| 位置 | `backend/alembic.ini` |

**现象**

`alembic upgrade head` 在 Windows 报
`UnicodeDecodeError: 'gbk' codec can't decode byte 0x8e`。
Python 的 `configparser` 按系统默认编码（中文 Windows 为 GBK）读取，
而文件是 UTF-8。Linux 默认 UTF-8，容器内无此问题。

**处理建议**

把 `alembic.ini` 里的中文注释改为英文，或在 `env.py` 中显式以 UTF-8 读取配置。
在修掉之前，Windows 上只能手工执行 DDL——这正是 D-004 的成因。

## 附：关于类型检查命令的重要提醒

根 `tsconfig.json` 是 `files: []` 的**引用式配置**，因此：

```bash
npx vue-tsc --noEmit                        # ❌ 什么都不检查，永远返回 0
npx vue-tsc -p tsconfig.app.json --noEmit   # ✅ 正确
```

前者即使源码中存在未定义变量也会通过。CI 配置时务必使用后者。
