## D-001　管理后台「一键补齐模拟患者信息」功能损坏　【2026-08-02 已修复】

| 项 | 内容 |
|----|------|
| 严重度 | **高**（用户可见功能完全不可用） |
| 位置 | `frontend/src/views/admin/sections/IdridImportSection.vue:142` |
| 发现方式 | 前端类型检查（`vue-tsc -p tsconfig.app.json`） |

**现象**

管理后台「IDRiD 批量导入」页中的「旧病例 · 一键补齐模拟患者信息」按钮，点击后必定报错，功能从未可用。

**根因**

前端调用了不存在的 API 函数，且后端也没有对应接口：

```
IdridImportSection.vue:142   await CaseImageApi.backfillPatientInfo({...})
                             ↑ frontend/src/api/case-image.ts 中未定义此函数
backend/app/api/v1/admin_import.py   仅有 POST /idrid，无补齐患者信息的路由
```

类型检查报错：

```
error TS2339: Property 'backfillPatientInfo' does not exist on type
              'typeof import(".../api/case-image")'
error TS2694: Namespace '".../api/case-image"' has no exported member
              'BackfillPatientResult'
```

**处理结果**

选了「补齐实现」——数据说明这功能确实需要：88 例训练病例**全部**缺姓名，
81 例缺年龄性别。

- 后端 `POST /admin/import/backfill-patient`，仅 ADMIN 可调，操作写审计；
- 生成是**确定性**的（由病例号 sha256 派生）：同一病例号永远得到同一组值。
  否则重跑一次数据就变一遍，已进 PACS 的 DICOM（PatientName 取自本字段）
  也会与业务库对不上；
- **筛查病例一律不碰**，哪怕开了强制覆盖。它对应真实受检者，
  往真实患者记录里塞编造的姓名，是把演示数据混进临床数据。
  返回结果里筛查侧显式报 0，而不是不报——不报会让人以为漏处理了。

与本项目此前拒绝伪造的字段划清界限：检查日期、眼别、像素间距、SNOMED 编码
一律不造，它们是**临床事实**，编一个会直接导致判读错误；
姓名/性别/年龄在教学病例里是**展示标签**，不参与判读，且界面明确标注为模拟。

实测：88 例全部补齐，已有年龄未被覆盖，筛查病例未被触碰。12 项测试固化边界。

## D-002　无金标准标注的病例无法拿到满分　【2026-08-02 已修复】

| 项 | 内容 |
|----|------|
| 严重度 | **中**（影响成绩公平性，但不影响功能可用） |
| 位置 | `backend/app/services/practice_service.py::_score` |
| 发现方式 | 补充 DR 分级测试时发现 |

**现象**

学员完全答对，总分也只有 85 分；对于没有病灶的病例（正常眼底、非 DR 病种），标注题永远拿不到满分。

**根因**

标注分公式为：

```python
score_annotation = accuracy * 70.0 + iou_avg * 30.0
```

当病例没有任何金标准标注时：

- `accuracy = 1.0`（学员没有漏标，判定为全对）
- `iou_avg = 0.0`（没有框可以计算 IoU）

→ 标注分恒为 `70.0`，连带总分上限变成 `100*0.3 + 70*0.5 + 100*0.2 = 85`。

**已固化**

该行为已由测试 `tests/test_dr_grade.py::test_known_issue_no_gold_annotation_caps_annotation_score_at_70` 显式固化，避免被误认为正常。修复时需同步更新该测试。

**处理结果**

先量化再决定，数据让判断变得没有悬念：

- 全库 **88 例训练病例中 82 例（93%）没有金标准标注框**；
- 已提交的 13 条练习里，**8 条标注分恰好卡在 70.0**。

也就是说这不是边角情况，而是绝大多数病例的主路径 —— 学员答得再对
也拿不到满分。

修正：`iou_cnt == 0` 时把 IoU 的 30% 权重并回召回率。只放宽「无从度量」，
不放宽「答错」，三条边界都有测试守着：

| 情形 | 修正前 | 修正后 |
|---|---|---|
| 无金标准框、学员也没标 | 70 | **100** |
| 无金标准框、学员乱标 | 0 | 0（不变） |
| 有金标准框、学员一个没标 | 0 | 0（不变） |

**历史成绩不重算。** 重算会让学员的成绩单在他毫不知情的情况下变动。
改为新增 `score_rule_version`（alembic 0012）：存量记录标为版本 1，
新记录为版本 2，报告页对版本 1 显示「旧版标注分规则」提示并说明
两者不可直接比较。这与此前 `scoring_mode` 的处理是同一思路 ——
口径可以改，但必须可区分、可解释。

## D-003　前端类型检查存在 47 处未使用变量　【2026-08-02 已修复】

| 项 | 内容 |
|----|------|
| 严重度 | 低（无功能影响） |
| 位置 | 多文件 |

**现象**

`vue-tsc -p tsconfig.app.json --noEmit` 报告 47 处 `TS6133: declared but its value is never read`，另有 1 处 `TS2345`（`screening/case-search.vue:706`，`string | undefined` 传入要求 `string` 的参数，存在潜在运行时异常）。

**影响**

数量过多会掩盖真实错误——本次修复中就发生过：一处调用了不存在的函数 `loadSource()`（实际应为 `fetchSource()`），因淹没在噪声中且当时类型检查命令有误而未被及时发现。

**处理结果**

**类型错误已归零**，可以纳入 CI 作为门禁。

`TS2345` 是真问题：`phoneMask(p: string)` 的函数体一直就处理了空值，
只是签名写死了 `string`。修的是签名，不是在调用处加 `!` ——
加 `!` 只是把类型系统骗过去，空值该来还是会来，错误挪到运行时。

清理过程中发现的**不是噪音的部分**已单独立为 D-008：
「未使用」的那批函数里，有相当一部分是完整实现却失去了 UI 入口的功能。
盲删会把问题藏起来。

## D-004　开发库从未被 alembic 纳管，迁移链未在任何环境验证过　【2026-08-02 已修复】

| | |
|----|------|
| 严重度 | **高（部署时才会暴露）** |
| 位置 | `backend/edu_eye.db`、`backend/alembic/versions/` |

**现象**

开发库里没有 `alembic_version` 表——它是 `Base.metadata.create_all()` 建出来的，
而不是由迁移建的。0001～0008 这条迁移链从来没有被完整执行过，
每次加字段都是手工 `ALTER TABLE` 打上去的。

**影响**

生产首次部署执行 `alembic upgrade head` 时，整条链会第一次真正运行。
其中任何一处与当前模型不一致（字段类型、约束、索引名、SQLite 不支持的
`ALTER`），都会在部署现场才发现，且此时已经有数据。

**处理结果**

原判断有一处不准确：并不是「迁移链应该能从空库建出数据库却建不出来」。
`0001_baseline` 是**刻意的空基线**，本项目的设计就是「表由 create_all()
建、迁移只做增量」—— 只是这一点从未写明，也没有任何护栏。

体检过程中查出四个真问题，逐一修掉：

1. **迁移链在 SQLite 上跑不到底**。`0004` 写死了 MySQL 专有的
   `ON UPDATE CURRENT_TIMESTAMP`，SQLite 报「near "ON": syntax error」。
   改为按方言取值，MySQL 环境结果不变。

2. **迁移版本号根本没有落库**。`env.py` 用 `connect()` 而非 `begin()`，
   SQLAlchemy 2.0 起 `connect()` 不再隐式提交，写入 `alembic_version`
   的 INSERT 随连接关闭一起丢弃。表现极具迷惑性：日志明明打印
   「Running stamp_revision -> 0010」，可版本表始终是空的，
   下次 upgrade 又从头跑一遍。

3. **开发库比模型少 11 个索引和 1 个外键**，因为它是更早的 create_all
   建的。其中两个是 `case_sn` 的唯一索引 —— 缺了它挡不住重复业务
   流水号，这不是性能问题而是数据正确性问题。已由 `0011` 补齐。

4. **`alembic.ini` 含中文，Windows 下读不了**（即 D-005），
   导致此前在 Windows 上根本无法执行迁移，只能手工 ALTER。

配套产出：

- `scripts/bootstrap_db.py`：全新部署的唯一入口（create_all + stamp head），
  库里已有业务表时拒绝执行；
- `env.py` 护栏：空库上直跑 upgrade 会被明确拦下并告知该用 bootstrap，
  而不是报一句「no such table」；
- `scripts/check_migration_chain.py`：五项体检，含**当前配置库的漂移检查**
  —— 只验新建的库等于没验，新库是 create_all 出来的，天然与模型一致。

开发库已 stamp 到 head 并升到 0011，此后一律走迁移，不再手工 ALTER。

## D-005　alembic.ini 含中文，Windows 下无法读取　【2026-08-02 已修复】

| | |
|----|------|
| 严重度 | 低（仅影响 Windows 开发机） |
| 位置 | `backend/alembic.ini` |

**现象**

`alembic upgrade head` 在 Windows 报
`UnicodeDecodeError: 'gbk' codec can't decode byte 0x8e`。
Python 的 `configparser` 按系统默认编码（中文 Windows 为 GBK）读取，
而文件是 UTF-8。Linux 默认 UTF-8，容器内无此问题。

**处理结果**

两处都做了：`alembic.ini` 保持纯 ASCII（文件顶部注明了这条约束），
`env.py` 里 `fileConfig(..., encoding="utf-8")` 作为第二道保险 ——
只改注释的话，下一个往 ini 里写中文的人还会踩同一个坑。

## D-006　DICOM SEG 病灶分割尚未接入阅片页　【2026-08-02 已修复】

| | |
|----|------|
| 严重度 | 中（能力缺失，非故障） |
| 位置 | `frontend/src/components/CoreRetinaStation.vue` |

**现象**

spike 阶段已验证 DICOM SEG 可以渲染成带透明通道的 PNG 掩码逐像素叠加
（传输量从 5.98 MB 降到约 214 KB），但正式阅片组件里的「金标准」图层
用的仍是矢量标注 `goldAnnotations`，没有接 SEG。

**影响**

IDRiD 这类数据集的金标准是像素级分割，转成矢量框会损失精度。
目前阅片页看到的金标准是框，不是真实病灶轮廓。

**处理结果**

已在 CoreRetinaStation 增加 SEG 掩码图层，画在 overlay 上、与标注共用
同一套坐标变换，缩放平移自动跟随。受 `layers.gold` 控制，练习模式下
连请求都不发 —— 请求本身会留在浏览器网络面板里，等于把答案递出去。
服务端也只在学员已解锁金标准时才下发 SOP UID。

实测：开启金标准 14352 px 掩码像素，关闭后 0 px。
「只验有、不验无」分不出是掩码在起作用还是别的东西恰好画了一片，
所以自检里两个方向都验。

## D-007　DICOM 实例的 SOP UID 依赖本地文件路径　【2026-08-02 已修复】

| | |
|----|------|
| 严重度 | 中（换机器/换目录后 DICOM 静默失效） |
| 位置 | `backend/app/common/dicom_convert.py:177`、`app/common/dicom_link.py` |

**现象**

转换时 SOP Instance UID 由 `deterministic_uid("sop", case_no, case_no, str(本地绝对路径))`
派生。阅片端要把界面上的图对应到 PACS 实例，只能用同样的输入重算。

一旦影像目录搬迁、或换一台机器部署，重算出的 UID 与 PACS 中已有的对不上。

**影响**

表现是「该病例不走 DICOM，退回 JPG」——不会配错图，但 DICOM 能力静默失效，
且没有任何提示，容易长期不被发现。

**处理结果**

1. `biz_case_image` 增加 sop / series / study 三列（alembic 0009），
   `dicom_link.uids_of()` 优先用落库值，取不到才回退重算；
2. `scripts/link_dicom_instances.py --apply` 已回填 88 张原图，
   全部与 PACS 核对通过；
3. 同一脚本不带 `--apply` 即为巡检，有失配以非 0 退出，可接定时任务。

落库了仍要与 PACS 核对：PACS 里被删过、或从未推送成功的，
光有 UID 不代表取得到像素。

## D-008　多个功能实现完整但失去 UI 入口　【2026-08-02 已修复】

| | |
|----|------|
| 严重度 | 中（用户看不到，代码里看着像好的） |
| 位置 | case-browse / screening / admin·NoticesSection |
| 发现方式 | 清理 D-003 的类型检查噪音时 |

**现象**

前端有一批处理函数实现完整（含 API 调用与错误处理），但模板里没有任何
元素调用它们。这类代码最危险的地方在于：**读代码的人会以为功能是好的**，
和 D-001 那个按钮是同一类问题的两面（D-001 是有按钮没实现，这里是有实现没按钮）。

清点结果：

| 功能 | 状态 |
|---|---|
| 病例归档 / 恢复（`onArchiveToggle`） | 后端 API、处理函数俱全，全系统无入口 → **本次已接上按钮** |
| 病例影像预览（`openPreview`） | 对话框与状态都在，只差按钮 → **本次已接上按钮** |
| 通知已读 / 全部已读（`markRead`/`markAllRead`） | 收件箱整块被换成「开发中」占位 → **本次已重建列表 UI** |
| ~~拖拽上传~~（`onFileChange`/`handleDrop`/`onDragOver`） | **误记，已更正**：上传早已抽成 `DiagnosisUpload` 组件（含拖拽），功能一直正常。这批孤儿是抽离时留在旧文件里的重复实现，连同只服务于它的 10 处死样式已一并清除 |

**已处理**

归档与影像预览接回了操作列——这两项后端完备、处理函数完整，只差一个按钮。

**收件箱重建时发现的更严重问题**

动手做 UI 之前先查了后端，发现**已读状态存在进程内存的字典里**
（`notice_service._read_set`），不是数据库：

- 后端一重启，所有人的已读全部丢失，消息又变回未读；
- 多副本部署时每个进程各存一份，同一个用户刷新两次看到的状态不同。

直接在这之上做界面，等于交付一个每次重启就失忆的功能。
**标记已读的唯一意义就是它下次还在** —— 这不是性能取舍，是功能本身不成立。

故先把已读落库（`biz_notice_read`，alembic 0013 + 0014），再做 UI：
消息列表、未读高亮、点行标记已读、全部已读、分页。
7 项测试固化，其中一条专门用新会话模拟「后端重启」。

存量已读状态无法迁移（它从来没落过盘），升级后所有消息回到未读一次。

关于机构权限申请：占位文案曾承诺该工作流。现按「同一个收件箱」处理 ——
将来它以新的消息类型汇入，而不是再开一块独立面板。

**一条自我更正**

初次清点时把「拖拽上传」也列为失去入口的功能，是错的 —— 只看到孤儿函数
就下了结论，没去确认功能是否由别处承担。实际上它早已抽成组件且工作正常。
判断一段代码是「死功能」还是「重构残留」，必须先找它有没有新的承载者。

**建议**

把 `vue-tsc -p tsconfig.app.json --noEmit` 纳入 CI 后，这类孤儿会在产生当天
就被发现，而不是攒到几十个之后才清一次。

## 附：关于类型检查命令的重要提醒

根 `tsconfig.json` 是 `files: []` 的**引用式配置**，因此：

```bash
npx vue-tsc --noEmit                        # ❌ 什么都不检查，永远返回 0
npx vue-tsc -p tsconfig.app.json --noEmit   # ✅ 正确
```

前者即使源码中存在未定义变量也会通过。CI 配置时务必使用后者。
